# Горячий резерв Кооператива

Основной сервер: Aeza 82.148.244.248. Резерв: Beget 85.198.67.48. С 17.11.2026.

## Как устроено

- **База.** Потоковая репликация Postgres: каждое изменение на основном через доли секунды
  есть на резерве. Слот `beget_slot` держит WAL, если резерв отстал (не больше 2 ГБ,
  `max_slot_wal_keep_size`), роль `replicator`.
- **Redis** (сессии игроков, состояние боёв) — копия основного (`--replicaof`).
- **Связь.** На основном контейнеры `koop-repl-pg` и `koop-repl-redis` (alpine/socat в сети
  `mmo90s_network`) открывают базу и Redis только на 127.0.0.1:15432 и :16379. Резерв ходит
  к ним SSH-туннелем `koop-tunnel.service` (ключ `/root/.ssh/koop_tunnel`, на основном
  ограничен `permitopen` на эти два порта, команды запрещены). На резерве туннель слушает
  172.17.0.1, контейнеры видят его как `host.docker.internal`.
- **Версия игры.** Автовыкатка после выката на основной отдаёт те же образы и коммит
  на резерв (`standby-gate.sh pull <sha>`). Игра на резерве не запущена,
  работают только `postgres` и `redis` с `docker-compose.standby.yml`.
- **nginx и сертификаты.** `refresh-certs.sh` достаёт сертификаты из последнего архива
  бэкапа основного (`/srv/backups/aeza`) и готовит сайты в `sites-available`, не включая.

## Проверить, что резерв живой

На основном:

    docker exec mmo90s-postgres-1 sh -c 'psql -U "$POSTGRES_USER" -d "$POSTGRES_DB" -c "select state, replay_lag from pg_stat_replication"'
    docker exec mmo90s-redis-1 redis-cli info replication | grep connected_slaves

На резерве:

    docker exec mmo90s-postgres-1 sh -c 'psql -U "$POSTGRES_USER" -d "$POSTGRES_DB" -c "select pg_is_in_recovery(), now()-pg_last_xact_replay_timestamp()"'
    docker exec mmo90s-redis-1 redis-cli info replication | grep link_status

## Автопереключение на Beget

Третий узел — Timeweb 195.133.81.121 (Амстердам), ТОЛЬКО свидетель: проверяет, жив ли
основной, данных игроков не хранит. Персональные данные россиян по 152-ФЗ хранятся в РФ,
поэтому реплика там 17.11 убрана вместе со старыми дампами. Третью копию с данными
ставить только на сервер в РФ.

1. `koop-lease-renew.timer` на Aeza каждые 15 секунд продлевает доступ игровой сети Docker.
   При сбое связи с Timeweb Aeza получает запасное подтверждение от Beget, пока PostgreSQL
   и Redis на Beget остаются репликами. Явный отзыв аренды Timeweb закрывает сеть.
   Ядро закрывает входящий, исходящий и внутрисетевой трафик игры по истечении 90 секунд
   без продления. `koop-lease-firewall.service` устанавливает закрытые правила до Docker,
   а маршрутизация остальных проектов работает отдельно. Мост и подсеть закреплены в
   `/etc/koop-lease-network`. При пересоздании сети этот файл надо сверить до запуска игры.
2. `koop-watch.timer` на Beget опрашивает HTTPS Aeza раз в 30 секунд. После 5 минут сбоя
   Beget проверяет свежесть обеих реплик, запрашивает независимую проверку на Timeweb
   и предварительно проверяет запуск игры и доступ к DNS. Если Timeweb подтвердил сбой,
   оба узла прекращают выдавать аренду Aeza. Beget ждёт по 150 секунд от блокировки каждого
   источника. Выдача запасной аренды и решение о повышении используют один `flock`.
3. Beget повышает PostgreSQL и Redis, запускает игру и проверяет контейнеры и HTTPS
   для kooperativ.space, www и admin. Все образы, включая PgBouncer, загружены заранее.
   Для запуска доступ к Docker Hub не нужен. Затем `dns-cloudflare.py` обновляет три A-записи
   одним запросом и сверяет оба авторитетных NS. Записи имеют TTL 60 и работают в DNS only.
   При сбое Cloudflare сторож повторяет только проверку и смену DNS.
4. Уведомления идут через `notify.sh` с настройками из `/etc/koop-notify.env`.
   Диагностика на Beget: `journalctl -u koop-watch` и `/var/lib/koop-watch/failover.log`.

Timeweb хранит только состояние аренды и проверяет готовность Aeza по HTTPS.
Отзыв в `/var/lib/koop-lease/revoked` переживает перезагрузку Timeweb. Два ключа
`/root/.ssh/koop_lease` имеют отдельные принудительные команды: Aeza может продлевать аренду,
Beget может проверять и отзывать. Ключ запасной аренды Aeza запускает только
`lease-peer.sh --renew` на Beget. Если Aeza не видит ни Timeweb, ни Beget,
игровая сеть закрывается по истечении аренды. При одновременной недоступности Aeza и
Timeweb Beget ждёт независимого подтверждения ограждения.
Репликация асинхронная, последние неподтверждённые на резерве изменения могут потеряться.

## Дополнительные игровые домены

Для кооперативспейс.рф, ммокооператив.рф и играйвкооператив.рф в Cloudflare
корень и `www` указывают CNAME на `kooperativ.space` в режиме DNS only с TTL 60.
Cloudflare разворачивает CNAME в адрес на корне зоны. Дополнительные записи при
переезде не редактируются: они следуют за главным игровым адресом.

До запуска адресов включить `infra/nginx/vhost-mirrors-bootstrap.conf` для HTTP-01.
После делегирования выпустить HTTPS-сертификаты с корнем и `www` каждого домена,
подготовить сертификаты и игровые виртуальные хосты на обоих серверах. API и
WebSocket обслуживает тот же игровой backend. Перед анонсом проверить HTTPS,
вход, чат и ответ `/ready` на каждом новом адресе, в том числе на резерве.

Проверка сценариев без доступа к продовым базам — `bash infra/standby/test-lease-peer.sh`.
При установке сначала обновить `watch.sh` и `lease-peer.sh` на Beget и настроить ключ,
затем обновить `lease-primary.sh` и юнит на Aeza. Порядок сохраняет ограждение
перед повышением даже во время установки.

Копии скриптов в работе находятся в `/opt/mmo90s-tools/standby` на Beget,
`/opt/mmo90s-tools/lease-primary.sh` на Aeza и `/opt/mmo90s-tools/lease-witness.sh` на Timeweb.
Юниты лежат в `infra/standby/systemd`. Токен с доступом к DNS находится только в
`/etc/koop-cloudflare.token` на Beget, права 0600. Запуск `dns-cloudflare.py --dry-run`
читает действующие записи без правок, а `failover.sh --preflight` проверяет локальную готовность
резерва без изменения ролей. Выключатель автоматического переключения на время работ:
`touch /var/lib/koop-watch/disabled` на Beget. Снимать его после восстановления нормальной репликации
и проверки `/ready` на Aeza.

## Возврат на основной

После переезда Beget становится единственным пишущим узлом. До ротации секретов
выкатка на старый основной блокируется. На Beget продолжает работать ежедневный pg_dump,
а поток WAL со старого основного выключается. Для длительной работы на Beget отдельно
перенастроить CD, продление сертификатов и потоковую архивацию WAL на новый основной.

Сохранить старые тома Aeza для расследования и пересоздать её PostgreSQL и Redis как реплики Beget.
При обратном переключении сначала подтвердить актуальность реплик и назначить окно работ.
Скрипты рассчитаны на направление Aeza → Beget; отзыв аренды сбрасывать только когда прежний
пишущий узел остановлен и переключение согласовано. Файл `peer-frozen` на Beget снимается
под `flock` сторожа после восстановления Beget в роли реплики PostgreSQL и Redis.

## Машина времени (откат на любую секунду)

Репликация не спасает от ошибки: удалённое на основном удаляется и на резерве. Поэтому на Beget:
- `koop-wal-receive.service` (pg_receivewal, слот `beget_wal_archive`) непрерывно пишет журнал изменений в `/srv/pg-wal`;
- `koop-pitr-base.timer` (04:30) снимает полную копию в `/srv/pg-base/<дата>` (`pitr-base.sh`), держит 7 копий, журнал старше самой старой удаляет.

Поднять базу на момент: `bash /opt/mmo90s-tools/pitr-restore.sh "2026-11-18 14:31:05+03"`. Живую базу скрипт не трогает:
восстанавливает во временном контейнере и кладёт дамп в `/srv/pg-restore/`, из которого берут нужное. Проверено 18.11 на живых данных.
