## 2.1. Что требуется

Форма протокола: `docs/qa/STAGE2_MANUAL_QA.md`. Шаблон с полным списком

(PASS/FAIL/BLOCKED), дата, исполнитель, ссылка на доказательство.

## 2.2. Правила прогона

1. Прогон выполняется на **отдельном аккаунте**, созданном для протокола, чтобы
   не портить статистику живых игроков.
2. Каждый сценарий с деньгами и предметами сопровождается скриншотом или
   выпиской из соответствующего журнала (`CurrencyLog`, `ResourceLog`,
   `ItemLog`, `UpgradeLog`, `ProductionLog`).
3. Вердикт FAIL не блокирует прогон: сценарий помечается, заводится задача,
   протокол продолжается. Приёмка требует нуля FAIL на момент подписания.
4. Дата и исполнитель обязательны: протокол без них — декларация, а не протокол.

# 4. Р-3. Репетиция миграций

## 4.1. Процедура

Репетиция выполняется на копии прод-БД, а не на чистой. Смысл — поймать то,
что ломается только на живых данных: нарушенные ограничения, длинные блокировки,
неожиданные NULL.

```bash
# 1. Снять свежий дамп прода
ssh vps-game "cd /opt/mmo90s && docker compose exec -T postgres \
  pg_dump -U mmo90s mmo90s" > /tmp/prod-copy.sql

# 2. Поднять отдельную базу для репетиции
docker run -d --name mmo90s-rehearsal -e POSTGRES_PASSWORD=x \
  -e POSTGRES_DB=mmo90s -p 55432:5432 postgres:16

# 3. Залить копию
psql "postgres://postgres:x@127.0.0.1:55432/mmo90s" < /tmp/prod-copy.sql

# 4. Применить миграции с замером времени
time DATABASE_URL="postgres://postgres:x@127.0.0.1:55432/mmo90s" \
  npx prisma migrate deploy

# 5. Прогнать сид и убедиться в идемпотентности
DATABASE_URL=... npx tsx prisma/seed.ts
DATABASE_URL=... npx tsx prisma/seed.ts   # второй прогон не создаёт дублей
```

## 4.2. Критерии успеха

| Критерий | Порог |
|---|---|
| Все миграции применились без ошибок | обязательно |
| Время применения | < 60 секунд на текущем объёме |
| Самая долгая блокировка таблицы | < 5 секунд |
| Повторный сид не создаёт дублей | `count` по каждому `code` = 1 |
| Данные Этапа 1 и 2 целы | контрольные суммы по `characters`, `item_instances`, `market_listings` до и после совпадают |
| Откат приложения без отката БД возможен | предыдущий образ поднимается на новой схеме |

Отчёт: `docs/qa/STAGE2_MIGRATION_REHEARSAL.md` — дата, объём базы, список
миграций, тайминги, вердикт.

# 5. Р-4. Решение по `SHIFT_READY`

## 5.1. Расхождение

Воркер `work-shift-finalize` пишет `ProductionLog.eventType = SHIFT_READY`.
В каноническом закрытом списке ТЗ 2.2 такого значения нет: там
`SHIFT_STARTED`, `SHIFT_CLAIMED`, `SHIFT_CANCELLED`, `SHIFT_FAILED`,
`OBJECT_STATUS_CHANGED`.

## 5.2. Решение: значение остаётся, канон расширяется

Обоснование: `SHIFT_READY` фиксирует реальный переход состояния —
момент, когда воркер перевёл смену в `READY_TO_CLAIM`. Это единственная запись,
по которой видно, что воркер жив и отработал вовремя. Если её убрать, пропадёт
наблюдаемость самого хрупкого места экономики: между `SHIFT_STARTED` и
`SHIFT_CLAIMED` может пройти неделя, и без промежуточной записи невозможно
отличить «игрок не забрал» от «воркер не отработал».

Работы:

1. Внести `SHIFT_READY` в канонический реестр событий ТЗ 2.2 (реестр отклонений,
   раздел 12 этого документа).
2. Убедиться, что админские выборки и аналитика знают о значении.
3. Добавить в метрики счётчик задержки: `SHIFT_READY.createdAt − shift.endsAt`.
   Медиана выше 120 секунд — алерт: воркер отстаёт.

# 6. Р-5. Решение по усталости зарплаты

## 6.1. Расхождение

В `work.formulas.ts` действует `dailyShiftSalaryCoeff`: каждая следующая смена
в сутках снижает зарплату шагом `salaryFatigueStep = 0.20` до пола
`salaryFatigueFloor = 0.20`. В канонической формуле ТЗ 2.2 этого множителя нет.

## 6.2. Решение: множитель остаётся, канон расширяется

Обоснование: без него суточный доход линеен по числу смен, и единственным
ограничителем остаётся потолок. Игрок, готовый кликать весь день, получает
ровно вдвое больше играющего полдня — то есть побеждает выносливость, а не
решение. Усталость создаёт убывающую отдачу: первые смены дорогие, последние
почти бесплатные, и «докликивание» становится бессмысленным само по себе, без
запретов.

Дополнительное обоснование появилось 15.08: суточный потолок стал двойным
(12 смен или 360 минут). На длинных сменах потолок достигается за четыре
захода, и без усталости эти четыре смены давали бы полную ставку каждая.

Работы:

1. Внести формулу в канон:
   `finalSalary = baseSalary × workerEfficiency × objectLevelCoeff × random × fatigue`,
   где `fatigue = max(floor, 1 − step × (shiftsToday − 1))`.
2. Записать в реестр отклонений как принятое отклонение от v2.2 с обоснованием.
3. Отразить усталость в интерфейсе: игрок должен видеть, что пятая смена
   принесёт меньше — иначе механика воспринимается как баг.
4. Учесть усталость в симуляторе дохода (сейчас профиль «worker» считает восемь
   смен по полной ставке — это завышает расчётный доход).

# 7. Р-6. Фильтры, сортировка и пагинация рынка

## 7.1. Что есть сейчас

`GET /api/market/listings` принимает `page`, `limit`, `type`, `mine`.
Этого мало: при сотне лотов покупатель не может найти нужное.

## 7.2. Контракт после доработки

```
GET /api/market/listings
  ?page=1&limit=20                     # limit ≤ 50
  &type=ITEM|RESOURCE                  # тип лота
  &q=строка                            # поиск по названию предмета/ресурса
  &priceMin=100&priceMax=5000          # диапазон цены
  &sort=price_asc|price_desc|created_desc|expires_asc
  &sellerId=uuid                       # лоты конкретного продавца
  &mine=true                           # только свои
  &status=ACTIVE|SOLD|EXPIRED|CANCELLED   # для «моих» лотов
```

Ответ дополняется блоком пагинации:

```json
{
  "items": [...],
  "page": 1, "limit": 20,
  "total": 137, "totalPages": 7,
  "appliedFilters": { "type": "ITEM", "priceMin": 100 }
}
```

## 7.3. Требования к реализации

- поиск `q` — по названию шаблона предмета и ресурса, регистронезависимо,
  через индекс; при пустой строке фильтр не применяется;
- сортировка по умолчанию `created_desc` — новые сверху;
- `total` считается тем же условием, что и выборка, одним запросом с `count`;
- невалидные значения — 422 с указанием поля, а не молчаливое игнорирование.

## 7.4. Требования к интерфейсу

- панель фильтров над таблицей: тип, поиск, цена от/до, сортировка;
- пагинация с номерами страниц и общим количеством, а не «показать ещё»;
- состояния таблицы: загрузка, пусто по фильтру, ошибка загрузки — три разных
  сообщения, а не одно «нет данных»;
- выбранные фильтры сохраняются в URL, чтобы ссылку можно было переслать;
- на мобильном фильтры сворачиваются в раскрывающийся блок.

# 9. Р-8. Симулятор читает сид

## 9.1. Расхождение

`simulate-economy.ts` импортирует `BalanceConfig`, но зарплаты, цены объектов,
выпуск ресурсов и стоимость ремонта задаёт собственными числами. Любая правка
сида не попадает в модель, и PASS симулятора перестаёт что-либо гарантировать.

## 9.2. Работы

1. Симулятор импортирует `PRODUCTION_OBJECTS`, `RESOURCES` и
   `PRIVATE_SHOP_RESOURCES` из `backend/prisma/economy-data.ts`.
2. Профиль «worker» строится по реальным объектам: длительность смены, оклад и
   выпуск берутся из таблицы, а не из констант симулятора.
3. Добавляется regression-тест: если в сиде появился объект, которого нет в
   модели симулятора, тест падает. Это защита от расхождения в будущем.
4. Профиль «worker» учитывает усталость зарплаты (раздел 6).
