# Инструкция администратора

Документ Этапа 5 (G7). Для администратора закрытого теста. Главное здесь — не
перечень кнопок, а **чего делать нельзя и почему**. Кнопки описаны в
`docs/specs/stage-5/STAGE5_ADMIN_API.md` с контрактами ручек; здесь — правила.

---

## 1. Три принципа, на которых стоит админка

**Всё обратимо.** У каждого действия записана обратная операция. Выдал миллион —
забираешь одной кнопкой, а не запросом в базу. Действие, которое нельзя
откатить, админу не выдаётся вовсе — такой кнопки не будет.

**Ничего без причины.** Каждое мутирующее действие требует текстовую причину
не короче 10 символов. Без причины ручка отвечает ошибкой (422), а не
выполняет. Причина уходит в журнал и видна в цепочке транзакций.

**Антиабуз не банит сам.** Он собирает сигналы и показывает их. Решение —
за админом. Автоматических банов по эвристике нет и не будет на закрытом тесте:
они поймают случайных, а не нарушителей.

---

## 2. Роли и что они могут

Три роли, менять их набор не нужно.

| Роль | Что может |
|---|---|
| **SUPPORT** | только смотреть: списки, карточки, логи, цепочки транзакций |
| **MODERATOR** | всё выше + бан, разбан, завершение зависшего боя, жалобы |
| **SUPER_ADMIN** | всё выше + деньги, предметы, заморозка рынка, справочники, premium, откат чужих действий |

Правка справочников и заморозка рынка — только у высшей роли: это меняет игру
для всех сразу. Роль пишется в журнал вместе с действием; если у аккаунта роль
позже сняли, старое действие остаётся в истории с прежней ролью.

---

## 3. Разделы

Тринадцать разделов. Мутации везде требуют причину и пишут обратную операцию.

| Раздел | Что делает |
|---|---|
| Пользователи | список, статус, бан/разбан, история входов |
| Персонажи | карточка, правка денег и опыта с причиной |
| Предметы | выдача, удаление, история экземпляра |
| Рынок | список, блокировка лота, заморозка рынка целиком |
| Экономика | сводка, суточные метрики, отклонения от коридоров |
| Бои | карточка боя, принудительное завершение зависшего |
| Кланы | состав, склад, общак, журнал, авторитет |
| Территории | владелец, заявки, принудительный сброс |
| Premium и помощники | срок подписки, выдача, отзыв |
| Логи | единый поиск по всем журналам |
| Жалобы | приём и обработка (в первой версии — почта админу) |
| Справочники | правка предметов, рецептов, цен без выката |
| Алерты антиабуза | сигналы детекторов с объяснением |

---

## 4. Обратимость на практике

| Действие | Как отменяется |
|---|---|
| Выдать деньги | списать ту же сумму |
| Списать деньги | вернуть ту же сумму |
| Выдать предмет | удалить выданный экземпляр по id |
| Удалить предмет | восстановить из снимка полей |
| Бан | разбан |
| Заморозка рынка | разморозка |
| Правка справочника | вернуть прежнее значение из снимка |
| Выдача premium | отзыв, снимок прежнего срока в журнале |

Откат — тоже действие: он тоже пишется в журнал, со ссылкой на отменяемое.

**Цепочка транзакций.** По любому предмету, сумме или персонажу — вся история
перемещений одним запросом, с общим correlation id по журналам денег,
предметов, ресурсов, производства и админских действий. Это то, чем ловят дюп
и перелив: без цепочки шесть журналов — просто много строк.

---

## 5. Чего делать нельзя

- **Не править деньги без причины.** Причина уходит в журнал и в цепочку
  транзакций; действие без неё не выполнится.
- **Не удалять предмет вместо отката операции.** Если предмет появился ошибочной
  выдачей — откати выдачу, а не удаляй экземпляр: откат вернёт и связанные записи.
- **Не менять справочники на живом проде без снимка.** Правка цен и рецептов
  меняет игру для всех; сначала снимок базы, потом правка.
- **Не банить по одному сигналу антиабуза.** Сигнал — повод посмотреть, а не
  приговор. Смотри цепочку и граф связей, потом решай.
- **Не сбрасывать район, пока по нему идёт бой.** Заявка останется без района.
  Дождись конца боя или заверши бой принудительно.

## 6. Вход в админку

Админ входит **отдельным логином**, не через игровой аккаунт: у админки своя
таблица учёток и свой вход. Адрес — `/admin`, игровой персонаж для него не нужен.

Учётку заводит сид: `admin`, роль `SUPER_ADMIN`. Пароль у неё на старте один
и тот же для всех установок — он записан открытым текстом в `prisma/seed.ts`,
поэтому **на боевом сервере его нужно сменить до первого живого игрока**: под
`SUPER_ADMIN` выдают деньги и предметы, сбрасывают районы и откатывают чужие
действия.

```bash
cd backend && npm run admin:password
```

Скрипт спросит пароль скрытым вводом и нигде его не напечатает. Аргументом
командной строки пароль не передаётся намеренно: аргументы видны в списке
процессов и остаются в истории шелла. Пароль из сида скрипт не принимает —
менять его на него же бессмысленно.

Деплой смену не откатит: сид делает `upsert` с пустым `update`, то есть
существующей учётке пароль не переписывает.

На проде — из контейнера бэкенда, пароль вводится в том же окне и внутрь
образа не передаётся:

```bash
docker compose -f docker-compose.prod.yml -f docker-compose.vps.yml \
  run --rm backend npx tsx scripts/set-admin-password.ts
```

Второй администратор заводится тем же скриптом: `-- --user петя --create
--role MODERATOR`. Роли — `SUPER_ADMIN`, `MODERATOR`, `SUPPORT`; что кому
доступно, описано в разделе 2.

## 7. Антиабуз: что показывают сигналы

Детекторы не наказывают — они объясняют, что показалось подозрительным, и кладут
это в раздел алертов. Реализованы семь из четырнадцати; остальные ждут данных,
которых пока нет (подробно — `docs/specs/stage-5/STAGE5_ANTIABUSE.md`).

Рядом с сигналами работают **жёсткие лимиты** — они молчаливые правила игры для
всех, не наказание:

| Лимит | Значение |
|---|---|
| Опыт с ботов | не более 40% дневного боевого опыта |
| Разница уровней в бою | опыт × max(0.1, 1 − 0.15 × Δуровень) |
| Передача денег одному аккаунту | не более 50 000 ₽ в сутки |
| Повторный бой с той же парой | второй и далее за сутки дают 25% опыта |

Эти лимиты описываются игроку в `docs/RELEASE_LIMITATIONS.md` — они честные
правила, а не скрытые ловушки.

## Оповещения в Telegram

Ночной воркер считает метрики в 03:00 UTC, и до утра пробитый порог никто
не увидит. Поэтому важное уходит боту.

Настраивается двумя переменными в `backend/.env` **на сервере** — в
репозитории их нет и быть не должно: доступ к админке не должен означать
доступ к боту.

```
TELEGRAM_BOT_TOKEN=<токен от @BotFather>
TELEGRAM_CHAT_ID=<id чата, куда слать>
```

`chat_id` берётся так: напишите боту любое сообщение и откройте
`https://api.telegram.org/bot<токен>/getUpdates` — он будет в
`result[].message.chat.id`.

Без этих переменных модуль молчит и ничего не ломает: оповещения —
дополнение к панели, а не замена ей. Настроен ли бот и доходит ли до него
сообщение, видно на вкладке «Обзор» кнопкой «проверить связь».

### Канал до Telegram нестабилен, и это учтено

На проде (Beget, Санкт-Петербург) измерено: холодное соединение до
`api.telegram.org` отваливается по таймауту примерно в каждой четвёртой
попытке, а следующая проходит за 70–100 мс. Проверено, что дело не в
настройках Node:

* DNS отдаёт и A, и AAAA; A-запись — настоящий адрес Telegram, сертификат
  подлинный;
* IPv6-связности у сервера нет вовсе, поэтому в окружение добавлено
  `NODE_OPTIONS=--dns-result-order=ipv4first` — без него часть запросов
  уходила в мёртвый IPv6;
* порог гонки семейств адресов (`--network-family-autoselection-attempt-timeout`)
  на долю отказов не влияет: сам IPv4-коннект временами не проходит.

Поэтому отправка повторяется до трёх раз с паузами 400 и 1200 мс — это
превращает четверть потерь примерно в полтора процента. Ответы самого
Telegram (400, 403) не повторяются: «chat not found» не пройдёт и с
десятой попытки, а повторять его — верный способ получить ограничение по
частоте запросов. Поведение закреплено в `src/tests/unit/telegram.test.ts`.
