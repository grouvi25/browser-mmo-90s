# Техническое задание: Фаза A, визуальная композиция боя

Версия: 1.0  
Дата: 2026-08-13  
Статус: READY FOR IMPLEMENTATION  
Проект: Kooperativ  
Основание: `APEHA_ADAPTATION_PLAN.md`, `APEHA_BATTLE_EQUIPMENT_VISUAL_RECON.md`

## 1. Цель

Перестроить боевой экран так, чтобы игрок за один взгляд понимал:

1. кто выбран целью;
2. где находятся бойцы на поле;
3. какой бюджет действий выбран;
4. куда будут нанесены удары;
5. какие зоны своего тела будут заблокированы;
6. какой итоговый план будет отправлен серверу;
7. сколько времени осталось до автоматического защитного хода.

Фаза меняет **визуальную композицию и клиентское взаимодействие**, но не меняет боевые формулы, API-семантику, серверный resolver, число зон, бюджет действий, таймер, сетку поля, расходники или награды.

## 2. Проблема текущего экрана

Текущий экран функционален, но смешивает на одном визуальном уровне:

- поле 9×5;
- HP;
- цель;
- движение;
- стойку;
- вертикальный список зон;
- счетчики ударов и блоков;
- четыре постоянно раскрытых кармана;
- оружие;
- журнал;
- таймер;
- подтверждение и сдачу.

Главный недостаток: удары и блоки выбираются в одном текстовом списке. Игрок вынужден читать маленькие кнопки и мысленно разделять «чужое тело» и «свое тело». В новой композиции удары выбираются на силуэте противника, блоки на силуэте игрока.

## 3. Границы фазы

### 3.1 Входит

- новая desktop-композиция боя;
- отдельный собственный силуэт для блоков;
- отдельный силуэт выбранной цели для ударов;
- визуальное отображение трех бюджетов действий;
- строка итогового плана;
- одна главная кнопка подтверждения;
- отдельное подтверждение движения;
- сворачиваемые карманы;
- сворачиваемый журнал;
- mobile-композиция без сжатия desktop;
- состояния загрузки, ожидания, ошибки, завершения и восстановления;
- keyboard/touch accessibility;
- визуальные и браузерные регрессии.

### 3.2 Не входит

- изменение формул боя;
- изменение вероятностей удара, блока, крита, удачи, ответа или уворота;
- новые зоны тела;
- новые типы действий;
- магия;
- новые расходники;
- смена оружия в бою;
- подкладки, модули, комплекты и обработки;
- новые API endpoints;
- новая схема БД;
- новый Redis-format;
- изменение 7-секундного таймера;
- изменение auto-action `block / defense4`;
- изменение гекс-сетки 9×5;
- изменение правил выбора соседней клетки;
- изменение PvE/PvP resolver;
- новые боевые ассеты, требующие генерации изображений.

Любое изменение из этого списка является отдельным change request.

## 4. Неприкосновенные контракты

### 4.1 Зоны

Используются существующие зоны:

- `HEAD`;
- `CHEST`;
- `RIGHT_ARM`;
- `LEFT_ARM`;
- `LEGS`.

### 4.2 Бюджеты

| Stance | Удары | Блоки | Пользовательское название |
|---|---:|---:|---|
| `attack2` | 2 | 0 | 2 удара |
| `mixed` | 1 | 2 | 1 удар + 2 блока |
| `defense4` | 0 | 4 | 4 блока |

### 4.3 SubmitActionOpts

Новая UI-композиция формирует существующий payload:

```ts
{
  stance,
  attackZones,
  blockZones,
  targetParticipantId,
  moveTo,
  itemInstanceId,
}
```

Запрещено переименовывать поля или менять их смысл.

### 4.4 Движение

- выбирается только соседняя свободная клетка;
- выбранное движение отправляется действием `move`;
- движение и зональный ход не отправляются одной командой;
- при выбранном движении зональный confirm недоступен;
- после успешного движения выбранная клетка очищается.

### 4.5 Таймер

- каждый доступный ход начинается с 7 секунд;
- при истечении времени отправляется `block` со stance `defense4`;
- визуальная переработка не создает второй таймер;
- при pending-запросе auto-action не отправляется;
- после завершения боя timer отключается.

## 5. Информационная архитектура

Боевой экран состоит из пяти уровней в строгом порядке:

1. **Статус боя**: раунд, ход, таймер, соединение.
2. **Поле**: позиции, доступные клетки, цель, HP.
3. **План хода**: стойка, свой силуэт, силуэт цели.
4. **Подтверждение**: текстовый итог и CTA.
5. **Вторичные инструменты**: карманы и журнал.

Запрещено помещать карманы или журнал выше подтверждения хода.

## 6. Desktop-композиция

### 6.1 Общая сетка

Контейнер `.battle-screen`:

```css
width: min(100%, 980px);
height: 100%;
display: grid;
grid-template-rows: auto minmax(250px, 1fr) auto auto;
```

Области:

```text
┌───────────────────────────────────────────────────────────┐
│ Battle status bar                                         │
├───────────────────────────────────────────────────────────┤
│                     Hex battlefield                       │
├───────────────┬───────────────────────┬───────────────────┤
│ Мои блоки     │ Стойка и план         │ Удары по цели     │
│ свой силуэт   │ счетчики/подтверждение│ силуэт противника │
├───────────────┴───────────────────────┴───────────────────┤
│ [Карман 0/4] [Журнал N]                    [Сдаться]       │
└───────────────────────────────────────────────────────────┘
```

### 6.2 Battle status bar

Показывает:

- слева: `Бой` и тип, если он уже доступен в данных;
- центр: `Раунд X / 30`;
- справа: `Ваш ход`, `Отправка…`, `Ожидание противника`, `Бой завершен`;
- таймер отображается горизонтальной полосой непосредственно под status bar либо внутри его нижней границы;
- число секунд обязательно продублировано текстом.

Не показывать одновременно «Ваш ход» и «Ожидание противника».

### 6.3 Поле

Сохраняется существующий `BattleGrid`, но визуально очищается от планирования зон.

Поле отвечает только за:

- позиции;
- цель;
- доступность движения;
- выбранное движение;
- союзник/противник;
- последнее событие;
- HP участников.

Цвета:

- игрок: синий или текущий союзный цвет;
- союзник: менее насыщенный синий;
- противник: красный;
- выбранная цель: красная рамка + target marker;
- доступная клетка: янтарный пунктир/контур;
- выбранная клетка: сплошной янтарный контур + маркер шага.

Выбранная цель должна отличаться от обычного противника не только цветом: добавить прицел/угловые скобки или подпись `ЦЕЛЬ`.

### 6.4 HP

Собственный HP и HP выбранной цели остаются у поля.

Требования:

- имя;
- числовой HP `current / max`;
- полоса;
- для нескольких врагов имя и HP меняются при выборе цели;
- изменение цели не сбрасывает уже выбранные зоны, если старая и новая цель живы и находятся в досягаемости;
- если цель умерла или исчезла, выбирается первый живой противник, attack zones очищаются.

### 6.5 Панель планирования

Desktop использует три колонки:

```css
grid-template-columns: minmax(170px, 0.8fr) minmax(240px, 1.2fr) minmax(170px, 0.8fr);
```

#### Левая колонка: «Мои блоки»

- заголовок `Мои блоки`;
- имя игрока;
- силуэт;
- пять интерактивных зон;
- выбранные зоны зеленые;
- counter `Блоки 2 / 2`;
- если stance не допускает блоки, силуэт остается видимым, но зоны disabled и counter `Блоки 0 / 0`.

#### Центр: стойка и итог

- segmented control из трех stance;
- краткое описание выбранного бюджета;
- счетчики ударов и блоков;
- текстовый итог плана;
- главная кнопка `Сделать ход`;
- при выбранном движении вместо нее `Перейти в клетку X:Y`;
- вторичная кнопка `Сбросить выбор`, только если есть выбранные зоны или движение.

#### Правая колонка: «Удары по цели»

- заголовок `Удары по цели`;
- имя выбранного противника;
- силуэт;
- пять интерактивных зон;
- выбранные зоны красные;
- counter `Удары 1 / 2`;
- если цель вне досягаемости, зоны disabled и текст `Цель вне досягаемости`;
- если stance не допускает удары, зоны disabled и counter `Удары 0 / 0`.

## 7. Силуэт зон

### 7.1 Реализация

Не использовать растровое изображение Apeha. Создать переиспользуемый React-компонент `BodyZoneSelector` из CSS/SVG-примитивов существующей стилистики.

Интерфейс:

```ts
interface BodyZoneSelectorProps {
  mode: 'attack' | 'block'
  selected: BodyZone[]
  limit: number
  disabled?: boolean
  disabledReason?: string
  onToggle: (zone: BodyZone) => void
  participantName: string
  hp?: { current: number; max: number }
}
```

### 7.2 Геометрия

Силуэт содержит кликабельные области:

- голова;
- корпус;
- левая рука;
- правая рука;
- ноги как одна логическая зона.

Минимальная интерактивная область каждой зоны: 44×44 CSS px на touch-layout. На desktop визуальная фигура может быть меньше, но hit area расширяется псевдоэлементом/оберткой.

### 7.3 Поведение toggle

```text
если zone уже выбрана -> убрать
иначе если selected.length < limit -> добавить
иначе -> не менять и кратко подсветить counter
```

Не заменять автоматически первую выбранную зону последней: это скрытое изменение намерения игрока.

### 7.4 Доступность

Каждая зона является `button`, а не `div`:

```text
aria-label="Удар: голова, не выбрано"
aria-pressed="true|false"
```

Для блока:

```text
aria-label="Блок: корпус, выбрано"
```

Порядок Tab:

- голова;
- корпус;
- левая рука;
- правая рука;
- ноги.

## 8. Stance selector

### 8.1 Поведение

При смене stance:

- attackZones очищаются;
- blockZones очищаются;
- selectedMove очищается;
- selectedTarget сохраняется;
- строка плана обновляется сразу.

Это сохраняет текущее безопасное поведение и не переносит несовместимый выбор между бюджетами.

### 8.2 Тексты

- `2 удара`, hint `Максимальная атака, без блоков`;
- `1 удар + 2 блока`, hint `Сбалансированный ход`;
- `4 блока`, hint `Полная защита, без атаки`.

### 8.3 Визуальные состояния

- default;
- hover;
- focus-visible;
- selected;
- disabled;
- pending.

Выбранная стойка должна определяться без цвета: рамка, вес текста и check marker.

## 9. Строка плана

### 9.1 Формат

Примеры:

```text
План не заполнен
2 удара: голова, корпус
1 удар: голова · 2 блока: корпус, ноги
4 блока: голова, корпус, левая рука, ноги
Движение: клетка 3:2
```

### 9.2 Валидация

Зональный ход готов, только если:

```ts
attackZones.length === budget.attacks &&
blockZones.length === budget.blocks &&
targetParticipantId exists when attacks > 0 &&
target is alive &&
target is reachable
```

`Сделать ход` disabled до полного заполнения бюджета.

Исключение: если серверная текущая логика сознательно допускает неполный выбор и дополняет его, это поведение должно быть подтверждено отдельным серверным тестом. По умолчанию ТЗ требует полный явный план.

### 9.3 Ошибки

Вместо общей `Ошибка` показывать:

- `Выберите цель`;
- `Цель вне досягаемости`;
- `Выберите 2 зоны удара`;
- `Выберите еще 1 зону блока`;
- `Эта клетка уже занята`;
- API message для валидного серверного отказа.

Ошибка выводится рядом с итогом, `role="alert"`.

## 10. Подтверждение движения

При выборе доступной клетки:

- поле показывает marker;
- панель зон визуально приглушается, но не исчезает;
- выбранные ранее зоны очищаются;
- центр показывает `Движение: клетка X:Y`;
- CTA меняется на `Перейти`;
- рядом появляется `Отменить движение`;
- после отправки CTA pending;
- при серверной ошибке клетка остается выбранной, чтобы игрок мог повторить или отменить.

## 11. Карманы

### 11.1 Закрытое состояние

Кнопка:

```text
Карман 2 / 4
```

Дополнительно показывать маленькие иконки заполненных слотов, без карточек и подробностей.

### 11.2 Открытое состояние

Inline disclosure под боевой панелью, не modal на desktop:

- 4 слота;
- название;
- эффект;
- доступность;
- кнопка `Использовать`;
- пустой слот не занимает высокую карточку;
- note `Состав выбран до боя и сейчас не меняется`.

### 11.3 После использования

- mutation использует существующий `use_item`;
- inventory invalidate остается;
- использованный предмет удаляется/обновляется;
- фокус возвращается на кнопку `Карман`;
- план зон не сбрасывается, если серверный контракт это допускает;
- таймер после успешного использования следует текущему серверному ходу, не перезапускается дважды.

- horizontal page overflow запрещен;

## 17. Синхронизация и race safety

- mutation double-click блокируется через `isPending`;
- CTA disabled сразу при отправке;
- auto-action проверяет pending перед отправкой;
- timer callback не использует stale `stance/zones` для ручного хода;
- refetch не сбрасывает локальный plan в том же раунде;
- смена `roundNumber` очищает zones/move;
- смерть цели очищает attack zones и выбирает новую цель;
- завершение боя отменяет interval;
- unmount отменяет interval;
- возврат на `/battle/:id` восстанавливает серверный state и начинает пустой локальный plan;
- `localStorage mmo_current_battle` сохраняется/очищается по текущим правилам.

Использовать:

- тонкие чертежные рамки;
- красную отметку удара как карандаш/штамп;

- янтарную разметку движения;
- моноширинные числа;

Запрещено:

- неон;
- стекло;
- fantasy ornaments;
- gradient text;

- постоянные крупные карточки для четырех пустых карманов;
- два одинаковых CTA;
- серый disabled без пояснения причины.

## 19. Motion

Разрешены только `transform` и `opacity`, кроме timer width, который сохраняет текущую линейную анимацию.

- выбор зоны: 100–140 ms;
- смена цели: 150–200 ms;
- planner sheet: 220–300 ms;
- pockets/log disclosure: 180–240 ms;
- event flash: до 500 ms;
- `prefers-reduced-motion` отключает non-essential animation.

## 20. Accessibility

Обязательно:

- WCAG 2.1 A/AA, axe без violations;
- field cells, targets and zones доступны с клавиатуры;
- выбранные состояния имеют `aria-pressed` или `aria-selected`;
- status changes используют `aria-live="polite"`;
- errors используют `role="alert"`;
- timer не объявляется каждую секунду screen reader;
- у иконок без текста есть accessible name;
- surrender имеет текстовое имя;
- focus-visible 2 px minimum;
- цветовой контраст 4.5:1 для текста;
- цвет не является единственным индикатором attack/block/move.

## 26. Стоп-условия

Реализация останавливается и требует отдельного решения, если обнаружено, что:

- backend допускает неполный зональный payload и продукт хочет сохранить это;
- target range нельзя надежно определить из текущего live state;
- auto-defense может конфликтовать с pending action;
- PvP требует отличного от PvE client contract;
- reload не может восстановить authoritative round/turn;
- сервер не возвращает данные для понятного waiting state;
- текущий item use считается отдельным ходом иначе, чем предполагает UI.

До ответа запрещено маскировать проблему локальным предположением.
